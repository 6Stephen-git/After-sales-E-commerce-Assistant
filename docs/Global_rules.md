# 全局规则与铁律

## 架构边界
1. Agent 1 → Agent 2 → Agent 3 的执行顺序由 Controller 控制。
2. Agent 4 为横向监督，Agent 5 为异步执行，均不参与主流程。

## Agent 独立性约束
1. 每个 Agent 必须实现为无状态纯函数，输入输出严格匹配 `schemas.py`。
2. Agent 内部禁止包含调度逻辑，禁止判断“何时被调用”“由谁调用”。
3. Agent 之间禁止直接互相导入或调用，所有数据传递由 Controller 完成。
4. Agent 在辅助模式和智能模式下共享同一套代码，不感知当前模式。

## 数据与接口约束
1. 所有 Agent 的输入输出必须严格匹配 `schemas.py` 中的 Pydantic 类。
2. 禁止自行发明字段名、修改字段类型或增删层级。
3. 如需新增字段，必须先修改 `schemas.py`，再同步到相关 Agent。
4. 所有变量、枚举值、日志前缀遵循 `Naming.md` 约定。

## 工具调用约束
1. 所有外部交互必须通过 `Tools.md` 中分配给本 Agent 的工具进行。
2. 禁止在 Agent 内部直接发起 HTTP 请求或数据库连接。
3. 工具不可跨 Agent 共享，各 Agent 只能使用自己的工具清单。

## 开发行为约束
1. 需求不清或文档中找不到的信息，必须反问，禁止自行猜测。
2. 一次只开发一个模块，按 `Roadmap.md` 定义顺序推进。
3. 每个模块开发完成并通过内嵌测试后，主动输出一条符合 `Changelog.md` 格式的变更记录，供开发者复制使用。

## 上下文处理原则
1. 每次调用 Agent 1 时，传入的 `materials` 必须包含纠纷自开始以来的全部对话记录和所有举证图片 URL。
2. Controller 负责维护对话历史缓存，首次全量拉取，后续增量追加，确保传入完整上下文。

## 质量测试与评估
1. 每个模块开发完成后，必须先通过自身嵌入式测试用例。
2. 前一个模块测试未通过，不得开始下一个模块。
3. 验收标准详见 `Evaluation.md`。

## 数据库写入限制
- Agent 1—4：禁止直接写入数据库
- Agent 5：仅允许写入判例库

## schema 修改权限
1. `schemas.py` 的修改权只有架构师拥有。Agent 禁止自行增删改任何字段。
2. Agent 发现当前 schema 无法满足需求时，必须在上报信息中说明：缺什么字段、为什么需要、影响哪个模块。
3. 禁止用 dict 绕过 schema 传递未定义的数据。
